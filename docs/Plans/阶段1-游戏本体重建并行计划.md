# 阶段 1：TH18 游戏本体重建并行计划

## 1. 目标与实现路线

重建 TH18 完整游戏本体，交付按模块组织、能够独立编译运行、保持原版行为的 C++ 源码。运行时由重建源码执行全部游戏逻辑，读取原版素材。

整体路线遵循上游的“还原 → 移植 → Web 适配 → 多人联机”。阶段 1 完成游戏还原，源码采用上游 `ports/<作品>/src/` 的组织方式；后续沿 SDL3、WebGL2、Emscripten 路线生成 Runtime，并接入统一 Launcher。依据：[作品进度](https://github.com/Ritosa2333/eagler-touhou/blob/main/docs/TOUHOU_PROGRESS.md)、[源码目录说明](https://github.com/Ritosa2333/eagler-touhou/blob/main/docs/architecture/source-layout.md)、[TH20 构建路线](https://github.com/Ritosa2333/eagler-touhou/blob/main/ports/th20/docs/DEVELOPMENT.md)。

确定以下实施条件：

- **行为依据**：本项目游戏目录内的日文 `th18.exe`、配套 `th18.dat` 和 `thbgm.dat`。游戏规则、边界行为和原版 Bug 均按该程序还原。
- **语言与构建**：C++20、CMake、MSVC、Windows x86。
- **本机宿主**：Win32、Direct3D 9、DirectSound；平台调用集中在平台模块。
- **源码位置**：`C:/Users/87804/Documents/playground/th18/ports/th18/`。
- **数据兼容**：原版配置、成绩、解锁数据和 Replay 格式双向互通。
- **执行编组**：1 名 Lead、3 名长期子代理，按下文批次并行推进。
- **工作规则**：每位执行者先读取项目 `AGENTS.md`、`stop-that-shit`、`stss` 和工具链说明。实现结果通过编译、实际游戏操作和原版录像回放确认。

## 2. 源码组织与协作接口

### 目录职责

以下路径均相对 `ports/th18/`：

| 目录 | 内容 | 负责人 |
|---|---|---|
| `src/core/` | 帧调度、计时、数学运算、随机数、公共状态 | Lead |
| `src/platform/` | Win32 入口、输入采集、窗口、文件操作 | Lead |
| `src/storage/` | 配置、成绩、解锁数据、录像编解码 | Lead |
| `src/resources/` | DAT、ANM、STD、MSG 读取与解释 | 子代理 A |
| `src/presentation/` | 绘图、文字、音频、HUD、菜单、对话、结局 | 子代理 A |
| `src/stage/` | ECL、敌机、Boss、关卡流程 | 子代理 B |
| `src/projectiles/` | 敌弹、激光、碰撞、伤害区域、消弹 | 子代理 B |
| `src/player/` | SHT、自机、射击、Bomb、受击与复活 | 子代理 C |
| `src/gameplay/` | 道具、计分、资源结算 | 子代理 C |
| `src/cards/` | 卡牌、商店、装备、使用、切换、解锁规则 | 子代理 C |
| `portable/` | 本机构建与启动脚本 | Lead |

各模块使用具体结构体和直接函数调用。共享头文件、根构建配置和主循环由 Lead 维护。每个源文件由指定负责人写入；跨模块修改通过对话交给文件负责人完成。

### 公共调用边界

Lead 在第一批次建立以下调用边界，并将原版字段含义写入对应头文件：

| 边界 | 生产者与消费者 | 确定行为 |
|---|---|---|
| `FrameInput` | Lead → 全部模块 | 提供本逻辑帧的持续按键、按下沿和释放沿；实机输入与录像输入进入同一处理路径 |
| `GameSession` | Lead 定义，各模块使用 | 保存模式、自机、难度、关卡、逻辑帧及会话状态；领域字段由对应模块维护 |
| 帧推进与绘制 | Lead → A/B/C | 每次逻辑推进执行一个原版逻辑帧；绘制消费当前状态；调用顺序按原版调度恢复 |
| 随机数调用 | Lead → A/B/C | 保存原版随机状态，恢复各随机函数和调用时机，录像恢复相同初始状态 |
| 资源读取 | A → B/C/Lead | 按原版资源名返回 DAT 条目字节及具体资源对象 |
| 动画与声音 | B/C/Lead → A | 使用原版资源名、脚本编号和音效编号创建、更新与结束表现对象 |
| 战斗结算 | B ↔ C | B 判定接触、命中、擦弹和消弹；C 执行自机受击、资源变化、掉落拾取及计分规则 |
| 卡牌作用 | C ↔ B/A/Lead | C 计算卡牌效果；对象所属模块执行状态变化；调用位置和先后顺序取自原版 |
| 商店 | A ↔ C | A 绘制商品与选择界面；C 管理商品生成、价格、购买、持有状态及离店结果 |
| 持久化 | A/C → Lead | A 提供菜单操作，C 提供进度变化，Lead 按原版格式读写文件 |

原版对象的创建、更新、销毁顺序由所属模块恢复。整数宽度、浮点运算、计时器和随机消耗顺序按照原版实现。

## 5. 完成标准与交付

### 构建与启动

在项目根目录执行：

```powershell
cmake -S ports/th18 -B ports/th18/build/native -G "Visual Studio 17 2022" -A Win32
cmake --build ports/th18/build/native --config Release
```

构建生成 `ports/th18/build/native/Release/th18.exe`。

启动参数确定为：

- `--game-dir`：原版素材所在目录。
- `--user-dir`：配置、成绩、解锁数据和 Replay 的读写目录。

构建与启动脚本使用上述同一组入口。

### 实际运行标准

1. **完整游戏流程**：标题、选人、难度、装备、正篇六关、商店、结局、Extra、练习、暂停、续关、结算和返回标题均按原版规则运行。
2. **资源解释**：原版游戏实际使用的 DAT、ANM、ECL、STD、MSG、SHT、音效和 BGM 内容进入对应实现。
3. **战斗行为**：四个自机、敌机、Boss、弹幕、激光、碰撞、擦弹、掉落和计分在实际运行中符合原版。
4. **卡牌玩法**：每张卡在对应场景中完成取得、装备或即时生效、使用、切换、冷却、跨关和解锁；共同作用的卡牌按原版顺序执行。
5. **录像回放**：先运行 DAT 内的四份 Demo，再运行原版保存的正篇通关与 Extra 整局录像；核对关卡推进、轨迹、受击、资源、商店选择与结束结果。
6. **数据互通**：重建版读取原版配置、成绩、解锁与录像；原版读取重建版写出的对应数据和原版输入录像。
7. **退出重开**：实际修改设置、获得卡牌解锁并保存成绩与录像，退出后重新启动，恢复相同用户数据。

实际出现的差异由对应模块负责人修正，并重跑出现差异的游戏过程。整局结果在对话中确认。
