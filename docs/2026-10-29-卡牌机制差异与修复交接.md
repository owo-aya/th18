## 01 念力反弹弹没有设置飞行速度

**范围：** `Psyco`，CardId `0x32`，主动卡。影响四机体装备该卡时的反弹攻击。优先级 P1。

### 当前已有实现

- [card_active.cpp](../ports/th18/src/cards/card_active.cpp) 的 `card_active_activate`、`card_active_update` 已实现发动、ANM、持续时间和冷却。
- [ecl_vm.cpp](../ports/th18/src/stage/ecl_vm.cpp) 的 `psyco_reflect_bullets` 已按范围寻找普通敌弹，生成 SHT 子程序 22 的攻击对象，再消除原敌弹；激光不参与反弹。
- [player.cpp](../ports/th18/src/player/player.cpp) 的 `player_attack_spawn` 先读取 SHT 的速度，随后在 `handler_a == 7` 分支计算向外反弹方向及随机角度扰动，但没有写入速度。
- 四份原版 SHT 的子程序 22 都是：初始速度 `0.0f`，发射处理器 7，伤害 16。当前后续运动按 `motion.speed` 计算，因此生成的反弹弹保持零速度。

定位：`player.cpp:1217`，以及 `ecl_vm.cpp::psyco_reflect_bullets`。

### 原有代码实现

原版链路：`0x410500`（念力更新）→ `0x45E930`（创建攻击对象）→ `0x45E320`（初始化）→ 发射表 `0x4B4230[7]` → `0x4613B0`。

`0x4613B0` 的关键行为为：

```cpp
angle = angle_from_player_to_reflected_bullet;
// 两点重合时采用原版的 pi / 2 分支。
r = gameplay_rng_signed_float(); // 原版 0x4CF288 随机流。
angle += r * degree_to_radian + r * degree_to_radian;
angle = normalize_like_original(angle);
attack.motion.angle = angle;
attack.motion.speed = 16.0f;       // 原版 attack +0x60 = 0x41800000。
```

SHT 的零速度是发射回调接管前的初值，不是反弹弹最终速度。

### 修复方式

1. 在 `player_attack_spawn` 的实际 `handler_a == 7` 分支补回 `motion.speed = 16.0f`，与方向初始化处于同一次创建调用中；同时按 `0x4613B0` 恢复扰动后的角度归一化。
2. 保留 SHT 子程序 22 的伤害、出生位置、所属资源和既有随机流；不修改原版 SHT，也不在念力更新中为每颗弹反复覆盖速度。
3. 核对后续 `player_attack_update → player_motion_init → player_motion_step` 使用新的速度，并继续由现有逻辑处理命中与离场。
4. 修复应覆盖四机体的同一发射处理器。不要给某个角色或某条关卡脚本单独设置速度。

## 02 地底太阳缺少发动当帧的无敌

**范围：** `Sun`，CardId `0x2F`，主动卡。优先级 P1。

### 当前已有实现

[card_active.cpp](../ports/th18/src/cards/card_active.cpp) 中，太阳的发动分支已经处理符卡状态、创建伤害圆、生成脚本 50 的视觉实体，并启动持续状态和冷却。持续更新分支也已经每次把自机无敌设为 2。

缺口在 `card_active_activate` 的 `Sun` 分支：发动时只执行 `spell_on_sun_card()` 和伤害圆创建，没有立即设置无敌。

当前执行顺序是卡牌更新 A `0x16`、自机输入与发动 A `0x17`、敌机 A `0x1B`、敌弹 A `0x1D`。按 C 发动时，本帧的卡牌更新已经结束；原本不处于无敌状态的自机要等下帧才得到持续更新赋予的无敌，留下发动当帧的受击窗口。

定位：`card_active.cpp:173` 和该文件 `Sun` 更新分支。

### 原有代码实现

原版 `0x40FB60` 在确认能够发动、处理符卡状态后，**先调用 `0x4099D0(2)`，再创建伤害源与视觉实体**。

`0x4099D0` 对自机计时块的赋值为：

```cpp
if ((player.flags_47784 & 1) == 0) {
    player.flags_47780 = 0;
    player.flags_47784 |= 1;
}
player.anim_id      = frames - 1; // 原版 +0x47774，previous。
player.invuln       = frames;     // 原版 +0x47778，整数当前值。
player.invuln_value = float(frames); // 原版 +0x4777C。
```

太阳传入 `frames = 2`。原版 `0x40F920` 在持续期间继续调用同一个设置函数。这是立即覆盖，不是取已有无敌时间与 2 的最大值。

### 修复方式

1. 在太阳成功发动的分支内，按原版顺序补回上述无敌计时块赋值，置于 `spell_on_sun_card()` 之后、伤害圆创建之前。
2. 冷却未结束、效果已经运行等拒绝发动分支不应设置无敌。
3. 使用已有等价函数，或直接复用这段真实赋值语义。不要仅写 `invuln` 而漏掉浮点当前值和 previous 字段。
4. 保留持续更新中的无敌刷新、功率扣减和退出条件；不能以延长持续时间补偿首帧缺口。

## 03 不死鸟之尾购入后的卡牌 HUD 越界

**范围：** `Mokou`，CardId `0x07`，以及持卡 HUD 的通用分组。优先级 P1。

### 当前已有实现

- [card_passive.cpp](../ports/th18/src/cards/card_passive.cpp) 的 `equip(Mokou)` 已将残机上限设为 7，并增加三次残机。
- 它返回 `false`，所以 [card_manager.cpp](../ports/th18/src/cards/card_manager.cpp) 的 `install_instance` 会将这张卡保留在实例列表中；这与原版一致。
- 卡表中 `Mokou.category == 3` 也与原版一致。
- [hud.cpp](../ports/th18/src/stage/hud.cpp) 的 `hud_refresh_cards` 却创建 `category_count[3]`、`category_index[3]`，直接以 `CardInfo::category` 为下标。

商店购买调用 `card_manager_acquire → hud_refresh_cards` 后，会访问这两个数组的下标 3。越界由代码路径确定；具体表现为显示异常还是其他内存影响，需要实机观察，不能预先声称已经发生崩溃。

定位：`hud.cpp:313` 起；保留卡对象的原因在 `card_passive.cpp::equip` 和 `card_manager.cpp::install_instance`。

### 原有代码实现

原版 `0x409DF0` 增加三残机后返回 0；`0x411460` 因而继续把卡对象加入列表。

原版 `0x408D00 → 0x408DE0` 使用的是卡对象 `+0x50` 标志，按三个 HUD 组排布：

```cpp
if (card.flags_50 & 0x08) group = 0;       // 主动卡。
else if (card.flags_50 & 0x40) group = 1;  // 装备卡。
else group = 2;                          // 其余保留的卡对象。
```

三个组的数量对应管理器 `+0x2C/+0x30/+0x34`，纵向原点分别是 0、130、260。不死鸟之尾属于第三组。卡表类别用于说明文字等用途，不等于这里的 HUD 分组下标。

### 修复方式

1. 将 HUD 的计数和排布两处统一改为上述对象标志分组，继续保持三个组。
2. 保留不死鸟之尾的对象、取得记录和原始卡表类别。不能通过删除该卡、将类别钳制为 2，或把数组扩成四组来回避原版语义。
3. 排布间距使用管理器的三个分组计数，其中包含 `Null`；绘制遍历按原版第三组 `CardInfo::unk_28 == 0` 跳过隐藏图标。原版计数与可见图标数并不相等，不能重算可见数量来改变间距；继续按实际卡实例绑定图标，不用 CardId 去重。
4. 与 09、10 共用 `g_card_objects[]/g_cards[]` 映射。购买、空白卡交换、跨关及录像恢复所触发的 HUD 重建都应进入同一修正路径。

## 04 早苗蛙弹卡的爆炸伤害区没有继承运动

**范围：** `SanaeOp`，CardId `0x0E`，SHT 子程序 14 的命中处理器 4。四机体装备该卡均受影响。

### 当前已有实现

[card_options.cpp](../ports/th18/src/cards/card_options.cpp) 已创建该卡子机并调用 SHT 子程序 14 发射；四份 SHT 的这组蛙弹都使用命中处理器 4。

[player.cpp](../ports/th18/src/player/player.cpp) 的 `player_bullet_hit_test` 已经在命中时创建一个持续 20 帧、初始半径 24、命中间隔 4 的圆形爆炸伤害区；半径增量也已读取 SHT `+0x4C`，该卡为约 1.3。

但是新伤害区只保留出生坐标，运动块仍为分配时清零的状态。原攻击对象随后走通用分支，把速度乘 `0.125f`、将 Z 写成 0.1；该卡 SHT 初始速度为 5，因此变成 0.625，而非原版的 2。

定位：`player.cpp:912` 至命中处理分支结尾。

### 原有代码实现

原版命中表 `0x4B41F0[4]` 指向 `0x460CB0`。调用顺序为：

1. 通过 `0x45DE40` 创建圆形爆炸源：半径 24、半径增量取 SHT `+0x4C`、寿命 20、伤害取当前 SHT 指令的 `int16 damage`。
2. 爆炸源 `+0x80` 设为 4，即命中间隔。
3. 原攻击 VM 收到 label 1，攻击对象状态 `+0x8C` 改为 2，速度 `+0x60` 改为 `2.0f`。
4. `0x40C720` 将原攻击对象的完整 `0x44` 字节运动块复制到新爆炸源的 `+0x1C`。因此伤害区会沿原运动方向继续移动。
5. 取消旧攻击伤害源的有效位，清空原攻击对象的伤害源索引，播放 SE `0x41`，返回原攻击对象的伤害值。

此分支没有通用命中中的 `speed *= 0.125f` 与 `z = 0.1f`。也不能与处理器 3 的魔理沙导弹爆炸合并：两者运动与寿命不同。

### 修复方式

1. 对 `handler_d == 4` 完整执行原版分支，保留已正确的圆形伤害参数。
2. 将攻击对象速度设为 2 后，再复制 `Motion` 到新爆炸源。不要只复制坐标或只给新伤害源设置一个固定向上的速度。
3. 该分支不要继续落入通用减速与 Z 偏移；恢复 SE 65、旧伤害源失效和索引清零的顺序。
4. 保留 SHT 伤害基数与攻击对象最终伤害的区别：爆炸创建读取前者，本次命中返回后者；蜈蚣等卡牌可能已经改过后者。
5. `card_passive_shot_hit` 中已有相近的运动复制写法可供核对，但红蛙卡的半径、寿命、伤害和 ANM 不同，不能直接套用整段参数。

## 05 早苗蛇弹卡遗漏命中特效与随机流消耗

**范围：** `SanaeOp2`，CardId `0x0F`，SHT 子程序 21 的命中处理器 5。影响命中表现及后续使用同一随机流的商店选卡。

### 当前已有实现

该卡的子机、SHT 子程序选择、蛇弹发射及转向更新已经存在。但 [player.cpp](../ports/th18/src/player/player.cpp) 的命中分派只显式处理 1、2、3、4 和红蛙特殊处理器，没有 `handler_d == 5` 分支。

因此蛇弹命中直接执行通用收尾，漏掉专用命中特效及其前置随机调用。[shop.cpp](../ports/th18/src/gameplay/shop.cpp) 的 `shop_random()` 使用 `card_rng()`；原版蛇弹特效也消耗相应的 `0x4CF280` 随机流，省略调用会使后续商店选卡的随机序列偏离。

定位：`player.cpp::player_bullet_hit_test`，约 888 行起；随机流入口为 `shop.cpp:45` 和 `core/rng.cpp`。

### 原有代码实现

原版 `0x4B41F0[5] → 0x460F30`：

```cpp
r = signed_random_float_from_4CF280();
angle = wrap(attack.motion.angle + r * 0.34906584f);
// 在 effect.anm 上创建脚本 149。
effect.position = attack.motion.position;
effect.rotation_z = angle;
// 完成模板绑定、初帧执行、入队。
return native_generic_hit_45F6F0(attack);
```

`0x45F6F0` 才负责随后设置 Z=0.1、速度乘 0.125、状态 2、退出标签、旧伤害源失效及索引清零。

与处理器 1 的 `0x45F9D0` 不同，`0x460F30` **不额外加 π，不执行处理器 1 的随机 RGBA 赋值**。二者虽然都创建 effect149，但不能整段复用。一次 `0x402810` 随机浮点调用内部使用一次 32 位生成；现有生成器的计数会增加两个 16 位步进，不应手工伪造计数。

### 修复方式

1. 增加处理器 5 的真实命中分支，先消耗 `card_rng()`，再创建并初始化 effect149，最后调用或执行已有通用收尾。
2. 使用正确随机流，不调用无参数的 `rng_next()` 代替。不要为“补齐次数”在商店或每帧循环中额外抽随机数。
3. 先写特效世界坐标与角度再执行 ANM 初帧，沿用现有独立托管方式管理寿命；不要预加游戏画面原点。
4. 保留命中处理器的返回伤害语义，以及旧伤害源、攻击对象、退出动画之间的生命周期。效果不能在命中当帧被直接释放。
5. 对照四份 SHT 的处理器 5 使用点应用修复；不要只修早苗角色本体的射击函数。

## 06 背后之门和鵺 UFO 误消激光

**范围：** `OkinaOp` CardId `0x13`、`NueOp` CardId `0x14`。两张装备卡的普通弹消除边界。

### 当前已有实现

[card_options.cpp](../ports/th18/src/cards/card_options.cpp) 的 `card_options_player_move` 已实现：

- 背后之门：随子机位置使用 20×6 矩形消弹，并生成寿命 2、伤害 4 的矩形攻击源。
- 鵺 UFO：围绕自机运动，在当前位置使用半径 6 的圆形消弹。

两者分别调用 `cancel_enemy_bullets_rectangle` 和 `cancel_enemy_bullets_circle`。这些公共函数位于 [ecl_vm.cpp](../ports/th18/src/stage/ecl_vm.cpp)，都会继续调用 `laser::cancel_*`，因而给两张卡增加了原版没有的消激光效果。

### 原有代码实现

- `0x40B9B0`：调用 `0x4294B0` 处理普通弹矩形消除，再调用 `0x45DFA0` 创建伤害矩形；**没有** `0x448F10` 激光矩形调用。
- `0x40BC50`：调用 `0x429370`，圆半径通过 XMM2 传入 6，栈参数包含掉落模式 0、数量上限 9999、普通弹消除标志 1；**没有** `0x449010` 激光圆形调用。
- 两处普通弹调用的最后参数 1 写入敌弹 `+0x678`，用于后续消失特效的 label 3 等处理。它与 07 中激光函数的“遵守消除免疫”参数不是同一个字段。

### 修复方式

1. 将两张卡改接已存在的普通弹专用入口：`cancel_ordinary_bullets_rectangle`、`cancel_ordinary_bullets_circle`。声明在 [stage.h](../ports/th18/src/stage/stage.h)。
2. 保留矩形尺寸、圆半径、子机运动、普通弹筛选和背后之门的攻击源创建。不要把公共 `cancel_enemy_bullets_*` 改成全局不消激光，太阳、月亮、小槌等调用者仍需要原有组合行为。

## 08 偶像护盾和两种保命卡使用固定速度计时

**范围：** `OptionBR` CardId `0x1E`、`AutoBomb` CardId `0x17`、`Rokumon` CardId `0x23`。

### 当前已有实现

[card_passive.cpp](../ports/th18/src/cards/card_passive.cpp) 的 `card_passive_player_update` 已有各项状态：

- 偶像护盾有四个独立的 0x14 字节计时块，起点 `card+0x54`，冷却门槛 360；挡弹后清零，恢复后重新显示护盾。
- 保命卡有持续状态和卡头 `+0x20` 计时块，到 60 后结束消弹并清除 Bomb 管理器的卡牌占用状态。

但四个护盾计时块、偶像卡头计时块和两张保命卡的卡头计时块都采用固定 `++integer`、`float += 1.0f`。游戏速度不是 1 时，它们与其他逻辑计时失步。

定位：`card_passive.cpp:335`、343、361 附近。

### 原有代码实现

原版 `0x40CEF0`、`0x40A560`、`0x40DA80` 按统一的计时块语义推进：

| 计时块内偏移 | 含义 |
| --- | --- |
| `+0x00` | previous，推进前的整数值 |
| `+0x04` | 当前整数值 |
| `+0x08` | 浮点累计值 |
| `+0x0C` | 本次推进清零的锁存字段 |
| `+0x10` | 计时标志，保留已有初始化语义 |

```cpp
previous = current;
latch = 0;
if (0.99f < speed && speed < 1.01f) {
    fraction += 1.0f;
    current += 1;
} else {
    fraction += speed;
    current = int(fraction);
}
```

护盾的单个计时块只在对应子机 `active == 2` 时推进；挡弹时先复位，随后仍执行本次推进。卡头计时块在该卡更新的尾部推进。保命卡先做消弹和 `current >= 60` 的结束判断，再推进卡头计时。

### 修复方式

1. 将上述真实计时块全部恢复成原版的整数快路径与浮点倍率路径，使用 `stage::g_speed_scale`。
2. 保留推进所在分支和先后顺序，不将四个护盾计时器移到无条件循环外，也不在检测结束条件之前提前推进。
3. 维持复位时 `previous=-1/current=0/fraction=0`、初始护盾 `previous=359/current=360/fraction=360` 的约定。
4. 不用整数 `current += int(speed)` 代替浮点累计，否则速度小于 1 时计时会停止；也不改成墙钟时间或固定毫秒数。
5. 07 和 08 修改同一共享分支，已有提交分别为 `7b3a298`、`7797bf2`；后续核对或补修仍由同一窗口负责。正常速度下的 360/60 门槛保持不变。

### 原有代码实现

原版虚表的两个专用槽为：

| 虚表槽 | 原版函数 | 作用 |
| --- | --- | --- |
| 17，字节偏移 `0x44` | `0x411090` | 接收该卡 HUD 图标句柄，写入卡对象 `+0x58` |

### 修复方式

1. 利用现有卡实例与图标映射恢复槽 17 的绑定语义；不需要引入通用虚表框架。重建、删卡和跨关时必须同步更新绑定，避免还引用旧图标。

4. 复用 ANM 已有 `scene_position` 的合成坐标机制；该实现位于 `anm.cpp`，当前为内部函数。确需跨文件调用时只暴露这项已有功能，不另造一套卡牌坐标算法。
5. 按原版位置、style 1、颜色及 alpha 接入现有文字系统。端口使用 1280×960 画布，按实际坐标模式进行一次换算，不能再次叠加 `(224,16)` 或凭视觉改字号。
6. 只补显示与相应生命周期；现有伤害倍率公式、累计与清零时机、录像值语义不属于本项的修改目标。

集成核对：原版坐标入队结果为合成屏幕位置加 `(-32,+32)`；端口 `scene_position` 返回 640 场景坐标，因此 1280 文字坐标为 `2 * position + (-64/S,+64/S)`，`S` 取已有显示模式倍率。`0x41A110` 只格式化并入队一次，再改最后文字项的 style；style 1 的字模宽 8、字符推进为 `6 * dirty_110`，两者不能混用。

## 11 法力经典强化咲夜 Bomb 时提前销毁旧波纹

**范围：** `MagicScroll`，CardId `0x1A`，对咲夜 Bomb 的强化效果。差异在波纹的存续和重叠，不是新增伤害数值问题。

### 当前已有实现

[bomb.cpp](../ports/th18/src/player/bomb.cpp) 的 `start_bomb` 已根据是否持有法力经典设置 `g_enhanced`。强化咲夜 Bomb 会在第 50、100、150 帧各创建一次 `pl02.anm` 脚本 24 的波纹，同时执行对应音效及两种伤害圆。

`update_sakuya` 在创建每轮新波纹前，却执行：

```cpp
if (g_secondary) anm_vm_free(g_secondary);
create_vm(24, &g_player->x, &g_secondary);
```

这会将仍在播放的上一轮直接删除。该文件的 `create_vm` 本身已经具备句柄替换时保留旧 VM 的处理：先以 `anm_manage_vm(*owner, nullptr)` 解除旧 VM 与持有槽的绑定，再将新 VM 绑定到同一持有槽。提前释放使这段既有寿命管理无法发挥作用。

定位：`bomb.cpp::update_sakuya`，调查版本约 283～290 行；持有槽替换逻辑在 `create_vm`，约 65～81 行。

### 原有代码实现

原版 `0x422960` 在上述三个时点创建脚本 `0x18`（十进制 24），执行初帧、加入普通 ANM 队列，并将新句柄写入 Bomb 对象 `+0x64`。**覆盖持有句柄之前没有销毁上一轮 VM 的调用。** 旧 VM 继续由 ANM 队列推进。

原版 `pl02.anm` 的脚本 24 已从 DAT 读取，相关时间安排为：

| 脚本帧 | 行为 |
| --- | --- |
| 0 | 建立图形、设置绘制层 12，并启动持续 120 帧的缩放 |
| 60 | 开始持续 60 帧的淡出及相关颜色过渡 |
| 120 | 执行删除指令 |

因此相隔 50 帧生成的波纹本来会重叠，上一轮还没有进入或完成淡出。当前实现将前几轮缩短到下一次创建时，破坏了原版的叠加与退场过程。

### 修复方式

1. 在 `update_sakuya` 中去掉创建新波纹前的直接释放，沿用 `create_vm` 已有的旧 VM 独立托管、新 VM 持有槽绑定逻辑。
2. 保证旧 VM 自行结束时不会清空新 VM 的 `g_secondary`。现有 `anm_manage_vm` 的解除旧持有槽逻辑就是处理这一实际关系，不需要增加新的波纹容器或寿命管理框架。
3. 保留原版第 50、100、150 帧的触发条件、音效、伤害圆，以及第 230 帧解除冻结的流程；不因修复视觉寿命改动伤害、计时门槛或添加额外的触发去重条件。
4. 波纹正常退场遵守脚本 24 的 120 帧寿命；关卡退出时继续通过现有 ANM/自机资源清理路径释放。核对这两个生命周期，不能用每轮创建时提前删除来代替退场清理。

集成核对：端口缓存自机 ANM 资源，`player_destroy` 不卸载该资源，因此 `bomb_end_run` 需要调用已有 `anm_delete_independent(40 + g_player_id)`，释放本关脱离持有槽的效果。

已有内容包括掉落转换、弹状态切换、半步位移和主弹动画退出。但没有按弹种创建独立的消失 VM，也没有在这条共用路径播放 SE `0x47`（十进制 71）。独立消失 VM 与原子弹收到退出标签是两次不同操作，不能视为已经由 `anm_interrupt` 完成。

### 原有代码实现

普通弹消除本体是 `0x428E90`。圆形入口 `0x429370`、矩形入口 `0x4294B0` 和直接消弹的卡牌回调都会到达它。主要执行顺序为：

1. 主弹 VM 走退出 label 1 并执行一次更新；有附属 VM 时，另行给其安排退出 label 1。
2. 检查原弹 `+0x20` 的 `0x200` 标志。在该标志未设置的分支中，按下述顺序处理特效、音效和掉落。
3. 读取原弹 `+0x674` 的消失脚本；脚本非负时，从普通弹管理器 `+0x7A41EC` 所指的 **`bullet.anm`** 创建独立 VM，设置原弹当前世界位置、执行初帧、加入普通 ANM 队列。
4. 原弹 `+0x678` 非零时，为新消失 VM 安排 label 3。该字段由普通弹消除入口的实际参数写入，和激光免疫参数不同。
5. 播放带原弹 X 坐标的 SE 71，再经 `0x4290E0` 处理本次掉落模式。脚本为负只跳过消失 VM 创建，不能连同本分支的音效一起省略。
6. 将弹状态 `+0xF68` 设为 4，执行半步位置修正，并复位消除状态所用的计时块。

`+0x674` 的生成依据在原版 `0x424FE0`：以 `0x4C5F90` 为起点、每种弹 `0x118` 字节的表，其 `+0x10C` 决定消失脚本选取方式，再结合颜色和专用映射取具体脚本。不能将所有普通弹统一成同一个消失动画。

全场消除 `0x4297A0` 也有相同的特效、音效与状态处理，但遍历条件不同，包含延迟弹。当前 `clear_all_enemy_bullets` 已在调用 `bullet_cancel` 前另行播放一次 SE 71；补齐共用入口时必须处理这处重叠。

### 修复方式

1. 从 `0x424FE0` 和原弹种表恢复本次消除真正需要的脚本选择与字段来源，接入已有普通弹对象。保留原版无消失脚本的分支，以及 `+0x20/0x200` 和 `+0x678` 的实际语义。
2. 在共用普通弹消除路径按原顺序创建独立消失 VM、播放位置音效、处理掉落，并对齐主弹/附属 VM 的退出与状态计时。不要在每张卡的更新函数内重复生成特效。
3. 复用 `g_cancel_effects` 和 `anm_manage_vm` 管理独立消失 VM，采用原弹当前位置；特效不能依赖即将释放的原弹对象继续存活，也不能提前加入画面原点偏移。
4. 将 `clear_all_enemy_bullets` 的现有音效调用与补齐后的路径统一，保证一次消除只执行原版次数的音效和掉落。按 `0x4297A0` 的标志分支处理，不能仅以当前 `delay == 0` 条件替代原版消除标志。
5. 保留各入口的普通弹筛选、数量上限、掉落模式、要石计数和激光调用约定。尤其不能给小槌重复生成金币，或让太子笏板多消耗随机数。
6. 与第 06 项一起处理普通弹的 `+0x678` 参数传递，由同一窗口负责 `ecl_vm.cpp/stage.h`。激光消失效果已经有独立实现，核对时区分两条调用链。

## 13 火力回复卡缺少原版浮字与饭团音效

**范围：** `Dango` CardId `0x06`、`PowerMax` CardId `0x20`、`Riceball` CardId `0x35`。已实现的火力增加数值不是本项差异；缺口在取得/发动后的完整反馈调用链。

### 当前已有实现

- [card_passive.cpp](../ports/th18/src/cards/card_passive.cpp) 的 `immediate(Dango)` 已增加 50 火力；`equip(PowerMax)` 已增加 100 火力。跨过火力档位时会播放 SE 13，但没有本次调用中的立即子机刷新和 `Power Up` 浮字。
- [card_active.cpp](../ports/th18/src/cards/card_active.cpp) 的饭团在火力未满时增加 100，跨档时刷新子机，随后播放 SE 13；同样没有创建 `Power Up` 浮字。
- 饭团在满火力时进入文件内的 `add_bomb_fragment()`，直接改 Bomb/碎片数，凑齐一枚时播放 SE 46。该分支遗漏饭团发动本身的 SE 13，也绕过了既有 `status_add_bomb_fragment` 的 HUD 刷新。
- 普通 P 道具已经通过 [pickups.cpp](../ports/th18/src/gameplay/pickups.cpp) 的 `popup(..., -1, 0xFFFFFF40)` 显示同类浮字。相关队列、字模与更新均已存在，但该函数当前只接受内部 `Pickup` 对象，没有供卡牌按世界位置调用的入口。

定位：`card_passive.cpp:157/181`、`card_active.cpp:111/207`，以及 `pickups.cpp::popup`。

### 原有代码实现

原版团子 `0x40A0B0`、狸猫卡取得效果 `0x40D390` 的共同顺序为：

```cpp
changed = add_power(amount);  // 团子 50，PowerMax 100。
clear_card_consumption_flag();
if (changed && player_exists) {
    refresh_power_options();             // 0x45D5E0。
    popup(player_position, -1, 0xFFFFFF40); // 0x4645F0。
    play_se_at(13, player_position.x);
}
```

`changed` 是是否跨过 `power_step` 的整数档位，不是只要增加了任意数值就触发浮字。团子即时效果返回 1、随后被消费；狸猫取得效果返回 0、继续保留为持卡对象。

原版饭团 `0x410BD0`：

- 火力未满：增加 100；返回跨档时依次刷新子机、创建同样的 `Power Up` 浮字、播放 SE 13。
- 火力已满：调用 `0x4576E0` 增加 Bomb 碎片，**之后仍播放 SE 13**。`0x4576E0` 负责 Bomb 上限、三碎片转换以及 HUD 刷新；转换成完整 Bomb 时还会经 `0x457690` 播放 SE 46。
- 两个分支之后才设置冷却并创建 `ability.anm` 脚本 66。即使 Bomb 已满、没有实际增加碎片，也仍执行饭团分支自己的 SE 13 和后续发动流程。

### 修复方式

1. 在现有拾取浮字实现上提供按世界位置提交的直接入口，复用现有轮转槽、字模和生命周期。可将内部 `popup` 的位置参数改为坐标，并让普通拾取调用者传入道具位置；不要为卡牌伪造一次拾取或复制另一套浮字系统。
2. 团子和狸猫取得效果在 `status_add_power` 返回跨档时，按原版顺序立即刷新子机、提交值 -1/颜色 `0xFFFFFF40` 的浮字、播放位置音效。保留当前即时取得条件和两种卡不同的消费/保留结果。
3. 饭团未满火力分支也采用上述反馈顺序，浮字和 SE 13 与原版跨档条件一致。不要把这项扩展为改变其加 100 火力、冷却或消弹半径。
4. 饭团满火力分支使用已经实现的 `status_add_bomb_fragment(&g_status)`，随后独立播放 SE 13；转换整 Bomb 时保留 helper 自身的 SE 46，满 Bomb 时也保留饭团 SE 13。
5. 保持 `start_cooldown` 和脚本 66 的创建顺序。狸猫卡的死亡后火力恢复是另一个回调，不应因补取得反馈而在那里新增浮字或取得音效。
6. 核对普通 P 道具与卡牌均使用同一浮字入口。当前普通 P 道具已有反馈，迁移参数时不能让其重复弹字或重复刷新。

集成核对：初始配卡虽然在工厂跳过取得效果，随后关卡开始的 slot13/slot0 仍会触发狸猫/团子反馈。原版 `0x442E53` 先创建浮字管理器，再于 `0x442F98/0x442FB7` 调用这两个槽；端口的 `pickups_create` 较晚，浮字槽清零已移至 `pickups_destroy`，保留关卡开始时提交的浮字。
